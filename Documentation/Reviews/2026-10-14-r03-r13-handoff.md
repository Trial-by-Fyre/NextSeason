## 4. Implementing R03

R03 is the problem that a notification is recorded as sent before iOS accepts it, so a scheduling failure loses it for good. Implement against the matrix's R03 section, as amended by revision 4.

### Design summary

1. **Four delivery outcomes.** Delivery returns `accepted`, `suppressed`, `failed` or `unknown`.
   - `suppressed`: alerts are not permitted, or delivery is disabled for this refresh.
   - `failed`: a definite scheduling rejection from `center.add`.
   - `unknown`: the request was submitted but acceptance cannot be established. Never retry it, because Apple re-alerts on a reused delivered identifier.
   - Cancellation alone never produces `unknown` (scenario 15's four cases).
2. **Per-show serialization.** One show's refresh work, from decision through scheduling and failure handling, never overlaps with other refresh work for that show.
   - Revision 4 change 1 (approved): another refresh **skips** a busy show. It neither waits nor makes its own decision for that show.
   - The state is in-process only, held by the single production `WatchlistRefreshService`.
3. **Guarded restore on `failed` only.** One new repository operation restores the previous `lastNotifiedSignature` and sets `pendingChangeSignature` to the undelivered signature.
   - It applies only if the stored row is still the same row (`dateAdded`), still active, and still holds the decision state this attempt wrote: the status signature and both notification signatures.
   - No timestamps are used for ownership.
   - It must run inside `SwiftDataWatchlistRepository.performWrite`, R01's rollback boundary, which includes the fresh-context replacement needed on iOS 18.
   - `InMemoryWatchlistRepository` must implement the same guard.
4. **Retry path.** A set `pendingChangeSignature` already forces a refetch (`awaitsConfirmation`), and `StatusChangeDetector.evaluate` notifies when it sees that signature again and it differs from `lastNotifiedSignature`.
5. **Suppression never sets up a retry,** and does not alter soft-change confirmation behavior (scenarios 4, 5 and 13).

## 5. Interactions to keep correct

1. **R11 coverage watermark.** `advanceUpdatesCoverage` re-reads every active row through `repository.all()` after the per-show loop.
   - A skipped busy show counts as covered only if its saved row already proves coverage.
   - A stale row counts only if this pass saved its stale flag (`staleSavedIDs`).
   - Forced passes never advance the watermark.
2. **R13 marks.** Catch-up marks and damage reports live in `WatchlistRowMarks`. A catch-up baseline silently clears any pending retry, which is the resume policy. Damaged rows go through the same baseline.
3. **R01 rollback.** Every repository write goes through `performWrite`, and the new guarded restore must too (R03 scenario 17).
