Fixes for the three Diagnostics and developer-tool findings in section 12 of [the feature-area review](2026-10-12-feature-area-review.md). Uncommitted; independent review pending.

**Risk: medium.** These changes affect developer and beta-diagnostics tooling only. They use familiar APIs, and no production refresh, persistence, or notification behavior changes. The consequence of an error is misleading test evidence, not user harm.

## Changes

1. **R15:** a new `DiagnosticsSimulations` class owns the runners, and the view's two buttons call it. The two-step runner and the delayed-pipeline runner are now separate, and each is kept until the watchlist show (matched by ID) changes. The runner still resets itself after a completed step 2.
2. **R16:** `analyze-performance-traces.py` checks each run against the evidence its Instruments template records. The suite records the expected run count as `runs_per_flow` in the manifest. Any gap marks the flow **INCOMPLETE**, unmeasured values show "—", and readiness becomes "not established". A measured failure still reports "Not ready". `report.json` gains `readiness` and per-flow `evidence_gaps`. In the comparison, a flow with no timing reads "Unknown".
3. **R17:** capture state stays in the parent shell. Ending a capture clears that state, so a second end does nothing. An EXIT/INT/TERM trap stops a stream when a run fails or is interrupted; INT and TERM exit through the EXIT trap, so cleanup runs once. Detection of streaming support no longer relies on a `grep -q` pipeline, which `pipefail` could misreport.

## Independent review, round 1 (ChatGPT)

The review found two P2 gaps in R16. Both are fixed, and each regression test was confirmed to fail without its fix:

1. **Missing timing or CPU evidence could still produce "Safe for beta".** Time Profiler flows now require the app's `flow.<name>` signpost interval and a readable `time-profile` table. Launch flows require time to first frame and a readable `time-profile` table. Network flows require neither.
2. **Invalid HAR content such as `{}` counted as measured.** A HAR now counts only if it has `log.entries` with at least one entry, and every entry has a `request` with a string `url`.

Result: `test-performance-evidence.py` ran 15 tests, all passing.

## Independent review, round 2 (ChatGPT)

One P2 gap remained: a CPU table with valid XML but no samples still counted as CPU evidence. The check now counts usable samples, meaning rows with both a weight and a symbol. It reports one of two distinct gaps:

1. **"CPU samples unavailable":** the table is missing or unreadable, or it has no usable samples.
2. **"CPU samples in the analyzed window unavailable":** usable samples exist, but none fall inside the window.

Each run in `report.json` now records `cpu_samples` and `cpu_samples_in_window`. Both new regression tests fail against the previous check. Result: `test-performance-evidence.py` ran 17 tests, all passing.

## Independent review, round 3 (ChatGPT)

One P2 gap remained: a sample with `<weight ref="…"/>` to an undefined id was treated as 1 ms and counted as measured CPU. Those rows are now skipped. A regression case covers every CPU table using only unresolved weight references; a second case confirms resolved references still count. Result: `test-performance-evidence.py` ran 18 tests, all passing.

## Assumptions and limitations

1. **The table names are unverified.** The required-table checks use the schema names the analyzer already used (`leaks`, `potential-hangs`, `live-allocations`, and others). No real trace was available to confirm them. If real exports use other names, sessions will report "not established" instead of a false pass. Check the first real session's evidence-gaps list.
2. **Launch flows do not record Leaks.** Their leak column shows "n/a", and readiness does not cover leaks for launch.
3. **An empty console log counts as missing,** on the assumption that every app run writes at least one log line under the capture predicate.
4. **An interrupted run's fallback log is not collected.** That run is never added to the manifest.
5. **App Launch traces are assumed to include CPU samples,** in the same `time-profile` table as Time Profiler traces. That is unverified. If they don't, every launch flow will report "CPU unavailable".
6. **The analyzed CPU window is the existing one:** from time to first frame to 15 seconds later, applied only when time to first frame is known. Samples with no sample time count as inside the window. In practice the window applies only to launch flows, so Time Profiler flows use all their samples. A HAR with valid structure but no TVMaze requests counts as measured.
7. **The analyzer exits 0 when evidence is incomplete,** printing a warning instead. The scripts run under `set -e`, and a non-zero exit would hide the report paths.
